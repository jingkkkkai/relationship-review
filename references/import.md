# 匯入規格

## IG

先識別實際結構，不假設固定路徑。常見為 `messages/inbox/<folder>/message_*.json`，也可能含其他前綴、訊息請求資料夾或多個分卷。從 `participants[].name`、`title`、`sender_name` 取匯出名稱；資料夾只作來源識別。不得根據資料夾後綴推測目前 @帳號或到 IG 查身分。

同聊天室所有 message JSON 都需處理，不只 message_1。已選定一位仍可能有多個歷史聊天室，合併前確認確為同人；初版預設一個私人聊天室。紀錄數含通知、轉傳、編輯版本，不稱人類發言數。

修復亂碼時保留原值，僅對可驗證的 UTF-8 錯誤解碼做轉換；不要對正常中文再次轉碼。`timestamp_ms` 依毫秒解析，顯示預設 Asia/Taipei，保留原 timestamp 與原位置。相同時間以來源順序穩定排列。

建立穩定 ID：來源檔案及原陣列位置（或對應的持久 ID）必須能回查；排序、加資料後不重新洗牌編號。保留編輯與撤回標記。跨分卷確定完全相同的紀錄才去重，保留所有原位置；不要把相同字句在不同時間的發言合併。

讀所有選定範圍文字及可讀圖片，包括聊天截圖。純 Reels／Threads 轉傳可排除實質分析，但保留排除計數與來源索引；對轉傳的討論不可刪掉。URL 僅作紀錄，不自動開啟。圖片 OCR 標示誤讀疑慮；無法確認時不要把 OCR 字句當確定證據。

附件路徑可能在聊天室外，必須依 JSON 實際引用查找，不能只拷貝單個資料夾。工具若未找到，列缺檔。音訊／影片只有環境真正播放或轉錄才算已處理；否則列數量及可能相關事件。電話通知／時長不能證明談話內容。

## LINE

接受官方聊天室匯出的 TXT，不把帳號備份檔當 TXT 匯入。檢查 BOM、UTF-8／UTF-16；其他編碼需根據檔案確認，不以取代字元悄悄丟失內容。

先檢視檔頭、日期行和數個樣本，適應平台與語系差異（日期格式、星期、12／24 小時、Tab／其他分隔）。檔頭的儲存日不是訊息日期。只有符合已驗證訊息格式的行才開始新紀錄，其他行可能是多行訊息延續；不能把內文時間或日期字樣一律當新訊息。

保留原行號範圍建立 `LINE-L000123` 等 ID；保留原時間字串、時區假設與來源檔。缺年份或時區不明時確認或標示推論，不能默默補精確時間。系統通知、收回訊息、通話、貼圖／圖片等標記分開處理，附件標記不代表附件內容已取得。訊息中的顯示名稱不一定是唯一帳號。

兩位發言者仍需知道誰是使用者。不要由順序或發言數推定。解析後抽查首尾、跨日、多行與系統通知，列出無法解析的行，不丟掉。

## 共用工作紀錄

內部正規化至少保留：`record_id, source_type, source_file, source_position, timestamp_raw, timestamp_local, timezone_status, sender_raw, kind, text_raw, text_display, attachments, version_status`。這是工作結構，不強迫使用者填寫。

多筆補述另外給固定 ID，不混為聊天證據。若同時提供 IG＋LINE，確認為同一對象及使用者希望合併，再對齊；支援兩種格式不代表自動合併。

外來 ZIP 不全量解壓：拒絕絕對路徑、`..`、符號連結及異常解壓大小，不覆寫原檔。若環境或資料格式不支援，說明具體缺口及可提供的替代格式。

## 明確的訊息編輯關係

從來源的 message ID、原訊息參照、版本鏈或其他明確編輯欄位核對原始訊息與其修訂，再依 [聊天格式](chat-style.md#編輯版本合併顯示) 建立 edit_groups。不能只用時間接近、相同說話者、相似文字或「已編輯」標記猜測哪幾則是同一訊息。原始傳送時間與修改時間分別保留；畫面採原始傳送時間，不能用最近修改時間把整則訊息移到後面。

仍逐筆保留原始匯出紀錄、位置、文字、附件與原始時間，版本關係作額外索引，不刪掉舊紀錄、不為畫面改寫閱讀筆數。只有最新版或編輯通知、缺少原始文字／時間／可確認目標時明示缺口，不發明歷史內容或倒推時間。
