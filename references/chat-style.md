# 固定的社群聊天閱讀格式

此為所有 session 的明確輸出規格，不自行改成 JSON 清單、除錯畫面或不同的表示法。保持單一 HTML，分析與完整脈絡功能不變。原始欄位、附件路徑、反應者與精確來源保留工作資料供查核，不在讀者的聊天旁印出。

## 給讀者看什麼

| 內容 | 固定顯示方式 |
|---|---|
| 一般文字 | 原文與原換行（郵件／手機部分遮蔽），不摘要、不改寫、不加 `content` 等 key |
| 訊息上的 reaction | 貼近該訊息顯示 `(❤️)` 等；每個不同 emoji 各一個括號，不顯示原物件、反應者欄位或帳號 |
| 獨立匯出的 reaction 紀錄 | 原時間位置顯示 `(❤️)`；有明確目標才可連回原訊息，不猜對象。沒有原時間不得編造新的回應事件 |
| Reels 轉傳 | `(reels)` 為原始網址超連結；無網址保留標記並說明未附連結，不顯示原物件、長網址或貼文標題 |
| Threads 貼文轉傳 | `(threads)` 為原始網址超連結；無網址保留標記並說明未附連結，不顯示原物件或貼文標題 |
| 其他未識別分享 | `(分享)`，不要把所有分享都當 reel／Threads |
| 圖片／影片／語音／檔案／貼圖 | 有可用原檔就直接顯示圖片／貼圖、語音／影片播放器或附件開啟連結；不以個資或 privacy_reviewed 阻擋。僅外部參照則提供手動點擊連結，缺檔或格式不支援才以短標記和原因呈現，不印原始路徑 |
| 回覆／引用 | 氣泡內先顯示引用框：你／他、原訊息時間、短預覽；可確定原訊息時連到原文。來源有引用但無法定位則顯示「原訊息無法定位」，無引用資料不猜 |
| 收回／編輯／通話 | `(訊息已收回)`、`(通話)`；有明確編輯關係時同一氣泡顯示最新版及 `(已編輯)`，舊版收在「編輯紀錄」，時間／位置採原始訊息。沒有歷史資料時只標已編輯與缺口，不補寫 |
| 系統紀錄 | 有已確認的白話內容就顯示，否則 `(系統通知)`，不把原始物件序列化給讀者 |

reaction 是紀錄，不直接證明認同、原諒或某種情緒。原物件含多個相同 emoji 可在視覺上合併一個標記；完整回應資料仍保留，不改變原始閱讀計數。若有完整回應者與數量需求，需使用者另行要求，不預設印出。

轉傳旁有使用者實際附上的話，應保留在標記後；之後對貼文的討論仍完整顯示、納入分析。貼文本身的介紹文不當成使用者留言。只有明確分享類型／來源網址能支持 reel 或 threads_post；不以訊息文字剛好提及「reel」決定格式。

為貼近聊天體驗，固定使用：日期分隔、每則顯示「你／他」與時間、你在右／他在左、系統訊息置中、保留段落和換行。左右由已確認身分設定；標籤預設不用匯出姓名，除非使用者特別指定替代名稱，不用發言數猜。未知時間直接標示未知。不要連續合併到失去訊息界線，不改動原順序。氣氛在片段標題顯示，不每句附一串分類。

聊天區不顯示原始紀錄編號、`kind`／`message`、來源路徑、`第 6578 筆`、JSON key 或原物件；不新增「查看 JSON」之類的讀者介面。分析的依據區也只顯示白話來源種類及必要短摘錄，仍以頁內連結到完整片段。內部 ID 與原位置映射保留作查核，但不作聊天內容印出。

## 工作資料如何交給內附工具

原 `records[].text` 及 `source` 保留原始內容與位置，不刪改來迎合畫面。另用以下**標準化顯示欄位**，不讓 renderer 猜原始分享物件：

- `display_type`：只能為 `text, reaction, reel, threads_post, image, video, audio, file, sticker, call, system, unsent, share, other`。每筆從已驗證的資料種類轉換；原始 kind 為 message／text 時可沿用文字。
- `speaker_role`：`self, other, system`，依已確認身分填寫；`sender` 保留原說話者供內部核對，不直接顯示，畫面標籤由 speaker_role 決定。
- `reaction_emoji`：獨立 reaction 的單一 emoji，例如 `❤️`；不是 JSON 字串，也不填 actor 名稱。
- `reactions`：附在訊息上的標準清單，例如 `[{"emoji":"❤️","actor":"內部保留的回應者"}]`；actor 不顯示。從原 `reaction`／其他欄位準確轉換，不要求使用者修改匯出檔。
- `comment`：非文字分享／附件中，使用者實際附上的文字；沒有就空字串。原物件、貼文摘要與系統格式不能放進 comment。
- `media_types`：訊息另含的附件種類，例如 `["image","audio"]`。實際路徑仍放原附件索引，不顯示在聊天；不知道種類則顯示附件標記，不猜內容。
- `system_text`：已確認的白話系統通知；未提供只顯示系統通知標記，不回退到輸出原物件。
- `version_status: "edited"`：只表示來源有編輯標記，不足以自動分組。有已確認的獨立版本紀錄時另外建立 `edit_groups`；沒有則標示匯出未提供可合併的舊版本。

例如一般文字含原始 reactions 時：`display_type: text, text: "謝謝你", reactions: [{emoji: "❤️"}]`，顯示原文與 `(❤️)`。reel 紀錄的 `text` 即使保留原物件字串，renderer 也只顯示 `(reels)` 超連結及經確認的 comment，不把 text 原樣印出。

這些縮略僅是閱讀格式，不代表模型可以略讀附件／訊息、刪除原始證據或改變歸屬。每筆紀錄仍有原位置與頁內錨點；只保留分享標記時，完整脈絡依然包括其前後討論。真正由使用者打出的 JSON／程式碼是聊天原文，仍須遮蔽郵件／手機後轉義呈現，不因長得像物件就刪掉。

## 交付前固定檢查

用虛構的一般訊息、附帶 reaction、獨立 reaction、reel、Threads、文字加附件及系統通知確認：標記精確、沒有序列化物件漏到畫面、沒有來源路徑、文字與順序未被刪減、所有來源仍可回查、單檔與五類篩選仍正常。不得用空白或刪掉整筆紀錄來通過檢查。

## 角色標籤的固定規格

預設畫面與分析的稱呼只用「你」「他」；不自動用來源中的真名、帳號、A／B 方或猜測的別名。身分對應不清楚時先確認，不靠左右位置或訊息數猜。選對象前的候選清單仍可顯示匯出名稱供辨認；確認對象後依本規則呈現。系統事件不構成第三個人的角色，置中顯示通知及時間即可。原文中提及的名字、第三人稱呼不擅自替換（郵件／手機依資料隱私規則遮蔽），以免改變語意；角色標籤統一並不代表全文匿名。

只有使用者明確要求替代名稱時，才在 report.json 與 archive.json 同時設定相同的 `display_names`，例如 `{"self":"小甲","other":"小乙","explicitly_requested":true}`。可只改其中一方。未指定就省略此欄；工具會預設「你／他」。不可因來源已含姓名就自行填 true。輸出概念組標題也依同一設定產生；整體責任／建議／支持等由模型產生的標題亦須遵守。

## 附件與引用的固定資料格式

不是要求使用者填寫：匯入後由模型／整理工具從原匯出欄位核對、轉換，保留內部映射，不猜缺失欄位。

- `share_url`：reel／threads_post 原始分享物件中的 URL，核對種類後填入；Reels 僅接受 instagram.com 及其子網域，Threads 為 threads.net／threads.com 及其子網域。僅 http(s)，保留原始帳號路徑、貼文 ID、編碼及查詢參數，不套郵件／電話遮蔽、不因簽名參數刪除連結；仍拒絕非 http(s)、含登入帳密的 URL 與不符平台的網域。不自動抓取貼文。連結文字固定 `(reels)`／`(threads)`，留言另保留。
- `media`：同一訊息可有多個附件，例如 `[{"type":"image","path":"photos/example.png","mime":"image/png"}]`。path 僅為 `--materials-root` 下相對路徑，不可跳出資料夾；原 attachments 索引仍保留。不需要 `privacy_reviewed`；舊資料有此欄也忽略，不因 false 或缺欄而擋住附件。文字遮蔽與附件原樣呈現的界線見 [資料用途與隱私](data-use.md)。
- type 為 image/sticker/video/audio/file。圖片支持 PNG/JPEG/GIF/WebP，音訊支援 MP3/MP4/OGG/WAV，影片 MP4/WebM；file 限 PDF／UTF-8 純文字並可下載。不支援的檔案標示原因，不強制改 MIME，不嵌入 HTML、SVG 或執行檔。媒體不自動播放。
- 有檔案參照時先在使用者提供的資料範圍內找檔，不得為省事只留標記。有原檔則由工具 base64 嵌入同一 HTML，離線能看；不放絕對路徑、不依賴另附資料夾。圖片／播放器可見，其他附件提供開啟或下載。僅遠端參照則用 `url` 取代 path，原樣提供點擊連結，不自動下載。缺檔使用 `reason` 白話說明，不補造圖。
- renderer 單一附件上限 25MB、不同本機附件總量 100MB；超限會停下說明，而非靜默遺漏或拆第二份 HTML。先釐清是否能提供合適的較小副本／縮減附件範圍，保持全部文字與缺口告知；不虛稱附件完整。
- `reply`：來源的明確 reply／quoted-message ID 可對上原訊息時，填 `{"source_verified":true,"record_id":"R001"}`。內附 renderer 用原紀錄產生引用框，240 字以上截為預覽並連完整原訊息，原文不截掉。也適用跨片段引用，點擊解除氣氛篩選並展開原文。
- 來源確有引用但目標不在資料中：`{"source_verified":true,"text":"來源確實保留的引用文字"}`；若連文字都未匯出就空字串。只顯示實際取得的文字和無法定位提醒。不把模型摘要寫進引用框。沒有明確引用資料則省略 reply，不能靠前後順序、相同文字或時間相近推定回覆目標。

交付前以虛構資料檢查：圖片實際有嵌入、無外部自動載入、連結標籤正確、缺檔原因可見、引用可回原文且解除篩選、跨片段引用及未定位引用都能區分；文字中的郵件／手機仍遮蔽；附件 href 原樣保留，圖片與語音無需隱私標記即可呈現，不把原始來源路徑印在畫面。原始文字保留只容許必要隱私遮蔽，不改語意與紀錄數。

## 編輯版本合併顯示

UI 固定使用「一則訊息、一個氣泡」：最新版在上方直接可見，下面是預設收合的「編輯紀錄（N 個舊版本）」，展開後依版本順序呈現原始及較早版本。主氣泡的說話者、日期分隔、時間與時間線位置，全以原始訊息為準，即使最後修改在隔天也不移到隔天。各版本的文字、附件、reaction 與明確引用均保留，不能只折文字卻遺失舊附件；文字仍遮蔽郵件／手機，附件與網址沿用原樣呈現規格。

在 archive.json 額外加入以下索引（不是使用者填寫格式）：

```json
{"edit_groups":[{
  "original_record_id":"R001",
  "version_record_ids":["R001","R003","R005"],
  "source_verified":true,
  "source":"原匯出中的明確訊息 ID／編輯參照及對應位置"
}]}
```

- version_record_ids 包含原始版本及後續修訂，最後一筆是已核對的最新版；順序與正規化後的來源紀錄順序相符。只能由原始資料或使用者明確提供的對應關係確認，不能把本例 ID 當偵測規則。
- 每筆仍留在 records 與原本 segments.record_ids 中，原位置和閱讀計數不變；每個版本只能屬於一個編輯群組。UI 在原始訊息的位置合併呈現，較晚片段的獨立編輯紀錄改為跳到該編輯紀錄的入口，不新增第二個訊息氣泡。反覆發相似文字而無明確版本關係，仍各自顯示。
- 每個原始版本的 `chat-record-` 錨點恰好一個：最新版在主氣泡，舊版在收折內容。連結或引用指向某個舊版本時，自動展開編輯紀錄，不能改跳到最新版而誤導查核。整組訊息的入口為 `chat-message-R001`，歷史入口為 `chat-edits-R001`。
- 引用仍顯示來源確實對應的那個版本；沒有資料就不能推測對方當時看到的是後來編輯的內容。全文搜尋仍可找到收折的舊版文字；舊版不是刪除。
- 分析按實際版本與時間理解回應；不能因 UI 在原位置顯示最新版，就將後來修改的文字當作當時已說過，也不能把一次修改重算為另一次獨立爭吵。舊版若影響責任、誤解或後續澄清，仍須納入前後文。

交付檢查：至少使用同日多次編輯、跨日編輯、跨片段編輯、引用舊版及相似但無版本關係的虛構案例，核對單一氣泡、原始時間與順序、舊版預設收合、所有 raw record 錨點唯一且可定位，閱讀覆蓋與附件規格不退回舊版。
