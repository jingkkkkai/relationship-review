# 補充事件

選定對象後，用下列範本一次邀請補充；可以直接貼文字或提供原有 JSON，也可以回答「沒有補充」。可選填想了解的部分，預設整體回顧，不預設分手或爭執。

```text
事件名稱：一起準備旅行
時間：六月上旬，確切日期不記得
來源：現在回憶／當時寫下的筆記
敘述：我記得對方整理交通資訊，我負責訂住宿。討論預算時有點不愉快，出發前重新談好。
想了解的部分（選填）：我們怎麼分工，以及意見不同時怎麼收尾。
```

快速格式也接受：`日期：敘述` 或 `事件名稱：敘述`。日期與事件名至少有一項；缺來源時暫列「使用者補述，形成時間未明」，不可硬列當時筆記。可同時輸入多筆。

內部轉成：`supplement_id, event_name, time_raw, time_range, date_confidence, source_kind, narrative, concerns, linked_record_ids, alignment_status`。事件名稱／日期不能當唯一 key；重名與更正保留固定 ID。原 JSON 的 key 可作標題，但不得把備忘錄最後修改日當事件發生日。

對齊文字及同時期訊息，保留相反證據：「使用者回憶沒有回應，但紀錄顯示有回覆」要並列說明，不能抹掉任何一方。只在缺口會實質改變判斷時追問；不要求精確日期、不要求重新聯絡對象。需要澄清時具體說明影響哪個判斷。

## 把補充納入事件，而非只列在缺口

補充是有價值的敘事來源，能支持「當事人這樣回憶／理解」，但不能單靠它確認線下事情客觀發生。不把「未獨立確認」誤寫成「沒有價值」或「一定不實」。當時筆記也不是對所記事件的獨立驗證。

對會影響理解、責任、建議或模式的重要補充，事件中並列兩個層次：

1. **從現有紀錄看**：只說可直接支持的經過及缺口，不以聊天沒有紀錄推定線下沒有發生。
2. **如果把這段補充也考慮進來**：以「如果 S001 的補充符合當時實際情況……」明確作假設，具體說明事件起因、各自選擇與責任、可改善方向會如何改變，及哪些結論仍不變。不只重述補充或泛寫「可能影響分析」。

第二層緊鄰顯示「依 S001 當事人補述作條件式分析，尚未獨立確認」，連到補述 ID 與對照紀錄。若包含多項事實，只假設相關部分成立，不一併假設敘述者對動機的解釋也成立。彼此衝突的補述分開呈現，不合成一個確定故事，也不預設使用者或另一方必然可信。

虛構例：紀錄顯示甲未回訊息；甲補充「先前見面已說今晚要陪家人」。可以寫：「只看訊息，還不知道乙是否事前知道安排。如果甲確實已清楚告知，這次就不宜直接歸為甲沒有交代；可以進一步看乙如何表達失落，以及甲能否在有餘力時確認彼此期待。這不代表乙的難過是錯的，也不表示甲必須隨時回覆。」整段附條件式注記，不能改寫成「甲事前已告知」。

若補述成立仍不改變結論，也說明理由。涉及安全或明確界線的敘事，可以提供不依賴裁決其真假的支持與選項，不必要求先證實才有資格被關心。

條件式分支可影響整體回顧，但保留其條件，標題與圖解亦同。模式索引分開記錄「原紀錄支持的案例」與「若補述成立才支持的案例」；不得把多筆同源補述當多項獨立驗證。更正、撤回補述時，同步回查所有條件式事件、模式及建議。
