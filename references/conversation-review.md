# 全部對話與完整脈絡

產出前必讀 [社群聊天閱讀格式](chat-style.md)。完整保留原始來源不等於把原 JSON、訊息 kind、路徑或紀錄位置印給讀者；聊天內容依固定標記與對話氣泡呈現，內部查核資料另留工作資料夾。

## 固定五類

只使用以下五類：

1. **開心與親密**：玩笑、甜蜜、分享趣事、表達喜歡。
2. **日常與照顧**：問候、生活分享、行程安排、關心彼此。
3. **討論與磨合**：說明想法、表達需求、釐清誤會、協調與修復。
4. **緊張與爭執**：不滿、指責、防衛與衝突升高。
5. **氣氛不明**：線索不足、指涉缺失、難辨反諷或無法可靠分類。

以連續對話片段分類，不逐句斷開。可以多標籤；先爭執後修復仍是同一片段時，標第三與第四類並保留轉折。無法確認時選氣氛不明，而非丟棄。不要以「哈哈」判定開心，或把有分歧的協調全部判成爭執；不是當事人內在感受的客觀測量。使用者更正後可更新標籤，原文不改。

全部匯出紀錄都有去處，包括轉傳、系統通知、已識別版本與附件標記；已確認的編輯版本依 chat-style.md 合併為一個氣泡、舊版收折，時間線採原始訊息，原始紀錄與閱讀計數仍完整保留；無氣氛線索的通知或純轉傳可歸氣氛不明，不需新增第六類。它們在分析中排除深入解讀，不等於在回顧刪掉。補述另外標示，不插進聊天假裝當時已說。

## 如何切片段及呈現依據

按話題開始、雙方回應、轉折及收尾建立連續片段，保持時間與原順序。不是每五句一段，也不按每次讀取上限斷開。同一事件跨日可有數段，附事件連結與前後段入口。長片段用展開／搜尋／導航改善閱讀，不截斷原文；大資料優先使用單檔內的收合、搜尋或動態呈現；不得未經使用者要求拆成多檔，也不能省略紀錄。

重要判斷的短摘錄只是入口，來源區必須有「看完整對話脈絡」連結到片段，讓讀者看見話題怎麼開始、說法在回什麼、後續澄清與收尾，並能繼續往前後看。前文約定、引用訊息或其他片段是理解所需時，一併連結；不要只連到一兩句的高亮錨點就算完整脈絡。支持與反例的片段都可達。若原資料缺前文或附件，明確標注缺失，不補寫。

完整回顧按日期排列，提供五類按鈕與文字搜尋；篩選只隱藏不符合片段，不能改原始排序或內容。同一 HTML 的分析區與回顧區以頁內錨點互相連結，深連結到被篩掉的片段時先解除篩選並展開，不能導到看不見的段落。

## 內附產出工具

讀完並分類後，建立 `archive.json`，不要由關鍵字腳本取代完整閱讀和分類。只用 `render_html.py --archive` 一次產出整合檔；`render_archive.py` 是內部區塊與驗證輔助，單獨執行只檢查資料，不輸出另一個 HTML。CLI：

```text
python3 scripts/render_html.py /path/work/report.json /path/outputs/關係回顧_網頁圖解.html --archive /path/work/archive.json --materials-root /path/work/materials
```

```json
{
  "title":"全部對話回顧",
  "reading_audit":{
    "sources":[{"source_id":"chat-1","source_kind":"message","record_count":2,"reviewed_ranges":[{"start":1,"end":2,"status":"read","note":"討論安排並確認時間。"}]}],
    "attachments":[]
  },
  "records":[
    {"id":"R001","source_id":"chat-1","position":1,"timestamp":"2026/06/01 10:00","sender":"我","speaker_role":"self","display_type":"text","kind":"message","text":"週末要不要一起吃飯？","source":"message_1.json 第 1 筆","attachments":[]},
    {"id":"R002","source_id":"chat-1","position":2,"timestamp":"2026/06/01 10:01","sender":"對方","speaker_role":"other","display_type":"text","kind":"message","text":"好，我來找餐廳。","source":"message_1.json 第 2 筆","attachments":[]}
  ],
  "segments":[{"id":"C001","title":"安排週末聚餐","date":"2026/06/01","categories":["日常與照顧"],"record_ids":["R001","R002"],"note":"依紀錄中的互動語氣整理，並非感受評量。"}]
}
```

`records` 依正規化後的穩定時間順序排列，時間不明保留原順序及說明。`position` 回到各原始來源從 1 開始的位置；每筆原始匯出紀錄都保留，連重複版本亦分別給來源 ID，避免閱讀計數與回顧脫鉤。`reading_audit.sources` 中每個來源需標 `source_kind` 為 `message` 或 `supplement`；supplement 已讀但不冒充聊天紀錄。訊息各來源紀錄數、位置與 archive 逐筆對齊。附件原始索引留工作資料，畫面採 chat-style.md 的附件預覽／連結與引用格式；本機原檔直接嵌入，不設個資檢查門檻，無可用原檔才標記原因，不自動載入外部圖片。稱呼固定用你／他，只有使用者特別要求才換名稱；來源姓名留內部，原文不擅自改寫，但輸出郵件／手機依資料用途規則部分遮蔽。

工具檢查每筆訊息恰好屬於一個主片段、無漏筆／重複／不連續切片，標籤只屬五類且至少一個。多標籤不重複複製原文；前後脈絡透過導航看，不把它再次算入覆蓋。

分析 JSON 加入：

```json
{"conversation_index":{"section_id":"conversation-review","segment_ids":["C001"]},
 "evidence":[{"id":"R001","type":"訊息紀錄","source":"message_1.json 第 1 筆","text":"聚餐提議的重點摘錄。","context_segment_ids":["C001"]}]}
```

`context_segment_ids` 可多個；每個訊息來源的依據都需至少一個有效片段 ID。使用內附工具時，產出分析的 CLI 必須加 `--archive archive.json`，實際核對 archive 的片段和紀錄 ID，而非只相信手填索引。補述的證據類型須明確，不要求虛構聊天片段。標為「訊息中的主張」也需要完整脈絡。

完整回顧包含選定對話原文，可能含第三人資訊，內嵌在同一份 HTML；不自動上傳、發布或分享。對話區預設收合，資料仍在檔案內。完整脈絡連結為 `#chat-segment-C001`，原文定位採 `chat-record-` 前綴，避免與分析依據 ID 衝突；由工具處理前綴，不更動來源 ID。點開脈絡時解除相關篩選並展開回顧區及片段，仍可回到分析區。交付前檢查全部錨點；預設文字中的郵件／手機部分遮蔽，附件與分享網址保持原樣，不因個資而隱藏；分享與額外匿名化須由使用者另行要求，不把未提供的其他聊天室納入。

附件的 `media`、原始分享 `share_url` 與引用 `reply` 規格依 [聊天格式](chat-style.md)，匯入時即建立來源映射，閱讀時核對，不在最後靠猜測補上。LINE TXT 未帶引用目標或附件原檔時明示限制，不承諾還原匯出未提供的聊天室功能。

編輯合併使用 archive 頂層 `edit_groups`，詳見 [編輯版本合併顯示](chat-style.md#編輯版本合併顯示)。不要為視覺合併刪改 records／原來源位置／segment 歸屬；跨段版本會保留跳回原訊息編輯紀錄的入口。驗證工具同時檢查版本存在、同發言角色、群組不重疊、順序有效及來源確認。這是呈現索引，不是模型已理解全部版本的證明。
